## 一、路径穿越（Path Traversal）

路径穿越也称路径遍历。以下内容来自 PortSwigger。

### 原理

设想一个购物应用，显示待售商品图片，可能会加载使用以下 HTML 的图片：

`<img src="/loadImage?filename=218.png">`

该 URL 会接收参数并返回指定文件的内容。图片文件存储在磁盘上，为了返回图片，应用程序将请求的文件名附加到基础目录，并使用文件系统 API 读取文件内容。换句话说，应用程序读取的文件路径是：

`/var/www/images/218.png`

该应用没有实现针对路径穿越攻击的防御措施，因此攻击者可以请求如下 URL，从服务器文件系统中获取任意文件：

`https://insecure-website.com/loadImage?filename=../../../etc/passwd`

这会导致应用程序从以下文件路径读取：

`/var/www/images/../../../etc/passwd`

`../` 序列在文件路径内有效，意味着在目录结构中向上提升一层。这三个连续序列从文件系统根节点逐步提升，因此实际被读取的文件是：

`/etc/passwd`

在基于 Unix 的操作系统中，这是一个标准文件，包含服务器上注册用户的详细信息，但攻击者也可以用同样的方法获取其他任意文件。

在 Windows 上，`..\` 和 `../` 都是有效的目录遍历序列。以下是针对 Windows 服务器的等效攻击示例：

`https://insecure-website.com/loadImage?filename=..\..\..\windows\win.ini`

### 如何发现

* URL 参数如 `?filename=218.png`、`?file=report.pdf`、`?path=/uploads/a.jpg`
* URL 中出现 `/static/...`、`/download/...`、`/loadImage?...` 这类"读资源"的端点
* 页面上有下载链接、头像、附件、图片等由后端读取本地文件返回的功能

### 实操

根据前端给出的图片源可发现网站路径，点击后进入路径图片。

![路径穿越实操：根据前端图片源发现网站路径](/img/server-vuln-1.png)

将网址参数改为 `?filename=../../../etc/passwd`，即可得到服务器上的目标文件。

## 二、访问控制（Access Control）

以下内容来自 PortSwigger。

### 什么是访问控制

访问控制是对"谁或什么"有权执行操作或访问资源施加约束。在 Web 应用中，访问控制依赖于身份认证和会话管理：

* **身份认证（Authentication）**：确认用户是他们声称的那个人。
* **会话管理（Session management）**：识别后续哪些 HTTP 请求来自同一个用户。
* **访问控制（Access control）**：决定该用户是否被允许执行他正试图执行的操作。

三者各司其职：身份认证确认是否登录；会话管理通过 cookie 和 session 确认当前会话属于谁；访问控制的逻辑判断是否有权限使用。

访问控制失效（Broken access control）很常见，而且往往构成严重的安全漏洞。访问控制的设计和管理是一个复杂且动态的问题，需要把业务、组织、法律上的约束落实到技术实现中。访问控制的设计决策必须由人来做出，所以出错的可能性很高。

### 垂直越权（Vertical privilege escalation）

如果用户能够访问其本不被允许访问的功能，这就是垂直越权。例如，一个非管理员用户能够进入管理员页面并删除用户账号，这就是垂直越权。

### 未加防护的功能（Unprotected functionality）

最基本的情况是：应用对敏感功能完全没有实施任何保护。比如，管理功能可能只在管理员自己的欢迎页面上有链接，而普通用户的页面上没有。但普通用户仍可能通过直接浏览管理功能的 URL 来访问它。

例如，某网站把敏感功能放在这样的 URL 上：

```
https://insecure-website.com/admin
```

这个页面可能任何用户都能访问，而不仅仅是那些界面上有链接的管理员。有时管理 URL 还会在其他地方泄露，比如 robots.txt：

```
https://insecure-website.com/robots.txt
```

即使 URL 没在任何地方泄露，攻击者也可以用字典对敏感功能的位置进行爆破。

### 隐晦式安全：隐藏 URL 不等于防护

在某些情况下，敏感功能会通过一个不太可能被猜到的 URL 来隐藏。这就是所谓的"**隐晦式安全（security by obscurity）**"。然而，隐藏敏感功能并不能提供有效的访问控制，因为用户可能通过多种途径发现这个被混淆的 URL。

设想一个应用把管理功能放在这样的 URL 上：

```
https://insecure-website.com/administrator-panel-yb556
```

攻击者可能无法直接猜出这个地址。但应用仍然可能把 URL 泄露给用户。比如，URL 可能出现在根据用户角色构建界面的 JavaScript 里：

```
<script>	
var isAdmin = false;	
if (isAdmin) {		...		
var adminPanelTag = document.createElement('a');		
adminPanelTag.setAttribute('href', 'https://insecure-website.com/administrator-panel-yb556');		
adminPanelTag.innerText = 'Admin panel';		...	}
</script>
```

这段脚本的作用是：如果用户是管理员，就在界面上添加一个指向管理面板的链接。**但问题是：包含该 URL 的脚本本身，对所有用户都是可见的，与角色无关。**

> 我的理解：服务器在渲染时对普通用户 `isAdmin=false`，页面上看不到入口，但前端 JS 里会把这个 URL 暴露出来。

### 基于参数的访问控制

有些应用在用户登录时就确定了其访问权限或角色，然后把这条信息存储在一个**用户可控的位置**，可能是：

* 隐藏字段（hidden field）
* Cookie
* 预设的查询字符串参数

应用根据提交上来的值做访问控制决策。例如：

```
https://insecure-website.com/login/home.jsp?admin=true
https://insecure-website.com/login/home.jsp?role=1
```

这种方式是不安全的，因为用户可以修改这个值，从而访问自己本无权使用的功能，比如管理功能。

应用**做了**权限判断——但判断的依据存错了地方。权限信息本该存在**服务端**（Session 里），却被放在了**请求里随用户来回传**。

```
❌ 错误：用户登录 → 角色=1 → 塞进 Cookie/隐藏域 → 每次请求带上 → 服务器信了
✅ 正确：用户登录 → 角色=1 → 存在服务端 Session → 请求只带一个不透明会话 ID → 服务器自己查
```

错误模式下，服务器做决策的数据来自客户端，而**客户端的一切都是攻击者可控的**——这就回到了那句核心原则：永远不要信任来自客户端的数据。

#### 三种载体

**① 隐藏字段**

```
<form action="/updateProfile"> 
 <input type="hidden" name="user_id" value="1001"> 
  <input type="hidden" name="role" value="user">
  </form>
```

**② Cookie**

```
Cookie: Admin=false;
```

**③ 查询字符串参数**

`?admin=true`、`?role=1`

### 水平越权（Horizontal privilege escalation）

如果用户能够访问属于**其他用户**的资源，而不是自己的同类资源，就会发生水平越权。例如，某员工不仅能查看自己的记录，还能访问其他员工的记录，这就是水平越权。

水平越权攻击的利用手法可能与垂直越权类似。例如，用户可能通过如下 URL 访问自己的账户页面：

```
https://insecure-website.com/myaccount?id=123
```

如果攻击者把 `id` 参数的值改成另一个用户的值，就可能访问到其他用户的账户页面，以及与之关联的数据和功能。

**注意（Note）**

这是一个不安全的直接对象引用（Insecure Direct Object Reference，IDOR）漏洞的例子。这类漏洞产生于：**用户可控的参数值被用来直接访问资源或功能**。

在某些应用中，可被利用的参数没有可预测的值。例如，应用可能不使用递增数字，而是使用全局唯一标识符（GUID）来标识用户。这可能让攻击者无法猜测或预测其他用户的标识符。然而，其他用户的 GUID 可能在应用中引用用户的**其他位置**泄露出来，比如用户消息或评论里。

> 攻击思路：通过水平越权遍历其他账户，直到找到权限更高的账户。
