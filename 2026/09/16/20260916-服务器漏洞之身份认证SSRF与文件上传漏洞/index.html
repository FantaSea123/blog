服务器漏洞之身份认证SSRF与文件上传漏洞

本篇整理自 PortSwigger Web Security Academy 的学习内容，覆盖身份认证漏洞（暴力破解、双因素认证绕过）、SSRF 两类攻击场景，以及文件上传漏洞与 Web Shell，附实操截图。

一、暴力破解攻击

暴力破解攻击是指攻击者通过反复试验来猜测有效的用户凭证。这些攻击通常通过用户名和密码的单词列表进行自动化。通过自动化这一过程，尤其是使用专用工具，攻击者能够高速进行大量登录尝试。

暴力破解并不总是完全随机猜测用户名和密码。通过利用基本逻辑或公开知识，攻击者可以微调暴力破解攻击，做出更有根据的猜测，这大大提高了此类攻击的效率。依赖基于密码登录的唯一身份验证方式的网站，如果没有实施足够的暴力破解防护，可能会极易受到攻击。

二、绕过双因素认证

有时，双因素认证（2FA）的实现存在缺陷，甚至可以被完全绕过。

如果用户先被要求输入密码，随后在另一个单独的页面上被要求输入验证码，那么在输入验证码之前，用户实际上就已经处于”已登录”状态了。这种情况下，值得测试一下：完成第一步认证（输完密码）后，能否直接跳转到”仅限登录后”的页面。偶尔你会发现，网站在加载这些页面前根本没有校验用户是否完成了第二步。

实操：2FA 简单绕过

输入目标账户和密码，发现存在二次认证。

直接手动修改 URL 跳转到登录后的页面。

三、SSRF：服务端请求伪造

什么是 SSRF

服务端请求伪造（Server-side request forgery，SSRF）是一种 Web 安全漏洞，允许攻击者诱使服务端应用向非预期的位置发起请求。

在典型的 SSRF 攻击中，攻击者可能让服务器去连接组织内部基础设施中仅限内网访问的服务；在另一些情况下，攻击者还能强制服务器连接任意的外部系统，从而泄露敏感数据，比如认证凭据。

简单来说，如果这个服务器有某些文件下载传输功能（服务器一般一只脚在内网，一只脚在外网），攻击者可以让服务器访问内网里的地址。因为服务器在内网里一般是畅通的，攻击者可以借助服务器在内网的访问得到数据。

针对服务器本机的 SSRF

在针对服务器的 SSRF 攻击中，攻击者使应用程序通过环回网络接口向托管该应用的服务器发送 HTTP 请求。这通常涉及提供一个带有如下主机名的 URL：127.0.0.1（指向环回适配器的预留 IP 地址）或 localhost（同一适配器常用的名称）。

攻击者通常也可以直接访问 /admin，但管理功能一般只对已认证用户开放，这意味着攻击者看不到任何有价值的东西。然而，如果对 /admin 的请求来自本机，常规的访问控制就会被绕过：应用程序授予对管理功能的完全访问权限，因为请求看起来来自可信位置。

应用为什么会这样表现——默认信任来自本机的请求？可能出于多种原因：

  1. 访问控制检查在另一个组件里。 这个组件位于应用服务器之前（比如反向代理）。当请求”绕回”服务器自身时（连接直接打到应用服务器，不再经过前置组件），检查就被跳过了。
  2. 灾难恢复预留的后门。 为了容灾，应用可能允许从本机发起的连接不经登录直接获得管理权限——万一管理员丢了凭据，还能从服务器上登进系统自救。这个设计的前提假设是：只有完全可信的人才会直接从服务器本机发起连接。
  3. 管理接口监听在不同端口上。 管理接口可能跑在主应用之外的另一个端口，用户根本无法直接访问到它。

这种信任关系——来自本机的请求被区别对待、优于普通请求——往往使 SSRF 成为严重（critical）级别的漏洞。

针对其他后端系统的 SSRF

四、文件上传漏洞

什么是文件上传漏洞

文件上传漏洞是指 Web 服务器允许用户向其文件系统上传文件，却没有充分验证文件的名称、类型、内容或大小。如果不能正确执行这些限制，哪怕只是一个基础的图片上传功能，也可能被用来上传任意甚至危险的文件——包括能在服务端执行的脚本文件，从而实现远程代码执行（RCE）。

在某些情况下，上传这个动作本身就足以造成危害；另一些攻击则需要后续发起一个针对该文件的 HTTP 请求，通常是为了触发服务器执行它。

此类漏洞在 CTF 中是十分常见的题型。

文件上传漏洞是如何产生的

考虑到文件上传的危险显而易见，真实网站里完全没有任何限制的情况很少见。更常见的情况是：开发者实现了一套自以为健壮的验证，但它要么本身就有缺陷，要么很容易被绕过。

例如，开发者可能尝试用黑名单拦截危险的文件类型，但在检查文件扩展名时没有考虑到解析差异；而且和任何黑名单一样，很容易遗漏一些更冷门但依然危险的文件类型。

另一些情况下，网站会通过验证某些属性来判断文件类型——而这些属性可以被攻击者用 Burp Proxy、Repeater 之类的工具轻易篡改。

最终，即使是健壮的验证措施，也可能在构成网站的多台主机、多个目录之间执行得不一致，由此产生的差异（discrepancy）就可以被利用。

文件上传漏洞有以下几类：

文件类型验证的缺陷（Flawed file type validation）

普通表单用 application/x-www-form-urlencoded（纯文本编码），传不了二进制数据；文件上传必须用 **multipart/form-data**，请求体被 boundary（边界线）切分成多个格子，每格一个表单字段：

filename、Content-Type、文件内容，全部由发送方填写。

三个字段

字段 起作用的阶段 决定什么
Content-Type 只在上传检查时 门卫放不放
filename（扩展名） 存储 + 执行时 服务器怎么对待这个文件（是否当代码执行）
内容 执行时 执行后发生什么

网站的验证手法与绕过

① 谎报 Content-Type：服务器只信请求里声明的 image/jpeg。

② 解析差异 / 漏网扩展名：.php 被拦了，还有 .php5、.phtml、.phar。

③ 图片马：服务器检查文件头字节（PNG 是 89 50 4E 47），那就拼一个”真图片头 + 尾部 PHP 代码”的合成文件。

Web Shell 与一句话木马

文件上传漏洞中危害最大的是 Web Shell（网页木马），最简单的形式是一句话木马。

网站允许你上传服务端脚本（如 PHP、Java、Python 文件），并且服务器配置为把它们当代码执行。这种情况下，在服务器上创建自己的 Web Shell 就是轻而易举的事。

Web Shell（网页木马）：一种恶意脚本，攻击者只需向正确的端点发送 HTTP 请求，就能在远程 Web 服务器上执行任意命令。

如果成功上传了 Web Shell，你就实际上完全控制了服务器——可以读写任意文件、窃取敏感数据，甚至以这台服务器为跳板攻击内部基础设施和网络外的其他服务器。
